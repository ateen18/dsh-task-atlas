# 任务图谱

`atlas_*` 工具维护的是一份**跨会话、按工作区持久**的项目蓝图。它存在的唯一理由：长对话里用户会忘记"原本要做什么、现在到哪、这件事为什么在这儿"。

所以你要维护的不是"我做了哪些操作"，而是**用户明天回来时需要的那个视图**。

## 什么时候用

- 用户说"帮我做/开发/实现/改/重构……"并且明显不止一两步 → 用。
- 纯问答、查资料、解释概念 → 不用，别硬套。
- 一个工作区第一次出现这种任务 → 先走启动拆解。

## 一、启动拆解（每个工作区一次）

### 先判定：白纸，还是有前情

**动手之前必须先调 `atlas_workspace_history`。** 它回答一个问题：这个工作区在本次对话之前，有没有别的会话。

这个判定决定接下来完全不同的两条路：

**情况 1 —— 没有历史（全新工作区）**

问用户一句：**快速拆解，还是详细拆解？**

- **快速**：你起草完整拆解交他校对。
- **详细**：按七个维度逐项问，问完再落盘。

**情况 2 —— 有历史（工作已经发生过）**

**不要重新盘问用户。** 那些对话里已经把需求、方案、试错、结论都说过一遍了，再问一遍正是这个插件要消灭的浪费。

1. 用 DSH 自己的会话检索工具（`session_search` / `session_event_search` / `session_event_read`）把历史会话读一遍。重点抓：真实的意图与约束、已经交付了什么、还在做什么、卡在哪、哪些是当时被否掉的方案和原因。
2. 用 `atlas_breakdown_draft` 起草拆解，`mode` 用 `fast`，然后 `atlas_breakdown_confirm` 落盘。
3. **明确区分来源**：告诉用户哪些条目是**从历史里读出来的**（可以指出出处），哪些是**你推断的**、需要他纠正。不要把推断说成事实——用户会照着这棵树干活。
4. 历史里没写到的维度（比如"明确不做什么"），宁可留空并说明，也不要编。

> 如果 `atlas_workspace_history` 返回 `NO_HISTORY_PROBE`（宿主没有会话查询能力），按**情况 1** 处理，并在对话里说一句"无法读取历史，按全新项目开始"。

### 七个维度（顺序固定）

1. 核心意图 —— 这个项目到底要解决什么
2. 核心交付物 —— 要交出去什么，每条都要能验收
3. 拆解 —— 1 / 2 / 3 / 4 的模块划分
4. 整体验收标准 —— 整体做到什么程度算完
5. 明确不做什么 —— 防范围膨胀
6. 约束与前置依赖
7. 优先级与先后顺序

流程：`atlas_breakdown_draft` 校验 → 有缺口就补（缺 `acceptance` 之类的警告不阻断，但要在对话里说出来）→ 用户确认后 `atlas_breakdown_confirm`。

**不要自行设置截止日期或工时**——这个插件不建模时间。

## 二、进行中

| 时刻 | 动作 |
|---|---|
| 开始做某件事之前 | `atlas_focus(nodeId)` —— 先声明你现在在做哪个节点 |
| 事情比计划里更细 | `atlas_node_add` 加一级（最多四层：项目 → 模块 → 任务 → 子项） |
| 计划里的描述不准了 | `atlas_node_update` 改标题/说明，别另建一个 |
| 一件工作真的交付了 | `atlas_node_done(nodeId, result)`，`result` 写**产出了什么 + 怎么验收** |
| 发现已完成的东西要返工 | `atlas_node_status` 到 `rework`，写清哪里不对 |
| 两件事有先后 | `dependsOn: [前置节点 id]`（add 和 update 都支持），见下 |
| 结构切错了 | `atlas_node_move(nodeId, newParentId)`，见下 |

### 前置关系（`dependsOn`）

`B.dependsOn = [A]` 读作 **A 是 B 的前置**：B 需要 A 的产出才能开始或完成。树里的 `⇢ 前置` 徽标和节点详情里的「本节点前置依赖」都是从这里来的（前置按它自己的状态上色，所以不用挨个点开就知道在等什么）。

**先分清三件常被混为一谈的事：**

| | 是什么 | 要不要画成边 |
|---|---|---|
| **依赖** | B 需要的某个输入是 A 的产出；A 没完成，B 只能等或只能硬猜 | ✅ 是 |
| **设计依赖** | B 建在 A 的结构/决定之上（例如"注入"建在"树结构"之上） | ✅ 是，但说明白"需要什么" |
| **排期** | "这个急""这个简单先做""按顺序做" | ❌ **不是依赖** |

排期不是依赖。把"先做"标成 `dependsOn`，图上就会长出一条假线，而假线比没有线更糟：
它会让别人以为 B 真的在等 A。

**判断的唯一方法：说出 B 需要 A 的什么。** 说不出来就不是依赖。

- ❌ 反例：「先跑通 A 再谈 B」→ 这是排期。除非 B 真的要用 A 跑通后的那个结果。
- ❌ 反例：「A 简单所以先做」→ 和依赖无关。
- ✅ 正例：「B 要用 A 产出的字段口径表」→ 依赖，因为 A 没交付，B 无从下手。
- ✅ 正例：「压缩后重注要用每轮注入那段文本的同一套预算」→ 设计依赖。

其它规则：

- 成环会被拒（`CYCLE`），自依赖和指向不存在的节点也会被拒。
- 模块是分组框，**不要给模块标 `dependsOn`**：模块之间的先后由里面节点的依赖推出来。
- 传空数组等于清空，不是追加。update 是整体替换。

**"少标"不等于"不标"**：某个工作区 33 个节点、8 个模块，一条前置都没登记，
于是每个节点的「本节点前置依赖」栏都是空的，用户第一反应是"插件坏了"。
有真实前置就登记，别让它空着；但也别为了让它不空而编造。
登记几条就够，不必把整个计划连成一条链。

### 重整结构（`atlas_node_move`）

层级是**按位置推导**的：把一棵子树挪到模块下面，它自己就从"模块"变成"任务"，它的子节点跟着降一级。

- 整棵子树不能超过四层，超了会被拒（`MOVE_REFUSED`）。
- 状态和变更历史原样保留——这正是它比"删了重建"强的地方。

### 关于 `result`

过程不进 `result`。不要写"我读了 A、试了 B、最后改成 C"，要写"现在 C 是什么、在哪、怎么验证"。

反例：`阅读了相关源码并尝试了三种方案最终修好了`
正例：`右侧面板宽度拖拽已修好（src/client/atlas-body.tsx:212）；验证：窄窗口 320px 下不再横向溢出`

### 产出要登记成「可点的把手」（`atlas_output_add`）

**`result` 是散文，`outputs` 是把手。** 只要这次交付里有一个"人回头会想再次打开"的东西，就必须登记，不能只写在 result 里。

反例（真实发生过）：

> result：`产出了一个带界面的内容分析终端，跑在 http://127.0.0.1:8511/ 上面`

地址只存在于一段话里，用户下次要用，就得回翻对话。正确做法是同时登记：

```
atlas_output_add(nodeId, label: '内容分析终端', target: 'http://127.0.0.1:8511/', note: '启动命令 npm run dev')
```

要登记的东西，包括但不限于：

| 类型 | 例子 |
|---|---|
| `url` | 本地跑起来的服务、在线看板、部署地址 |
| `file` | 报告、文档、图表、导出的 csv/xlsx、关键代码文件 |
| `dir` | 产物目录、数据目录、项目子模块 |

规则：

- **一个交付物一条**。同一个 target 重复登记会覆盖，不会重复。
- `label` 写人话（「月度复盘报告」而不是 `report.md`）。
- `note` 写怎么用（启动命令、依赖、注意事项）。
- 地址变了就 `atlas_output_remove` 旧的再登记新的——**留下死链接比没有更糟**。

### 关于层级粒度

- **模块**（第二层）= 一个能独立验收的交付物。不要拆成"读代码""写代码""测试"这种动作序列。
- **任务/子项** = 具体能一两次操作做完的事。
- 宁可少拆：节点太多，用户又要在树里迷路——那就换了个地方迷路。

### 标题怎么写（这条被违反过一次，代价是整个图谱不可读）

**标题是一行标签，不是一句话。** 树是用来扫的：一行一个节点，读得完才算树。

- **≤ 18 字**，一行扫完。超出会给警告（不阻断）。
- **不要在标题里塞解释**：写「基线对齐」而不是「基线对齐：确认数据文件与视频文件的真实路径、字段口径、样本量」。
  工具会自动把冒号后面的内容搬进 `note`，但**别指望自动搬运**——它只在左边像标题、右边足够长时才拆。
- 解释、背景、验收标准 → 放 `note`。
  已交付的东西 → 放 `result`（只写"产出了什么 + 怎么验收"）。
- 子项尤其要短：用户扫的是"还剩什么"，不是"这一项为什么重要"。

反例 / 正例：

| 反例 | 正例 | 解释去哪 |
|---|---|---|
| `基线对齐与数据盘点：确认数据文件与视频文件的真实路径…` | `基线对齐与数据盘点` | note |
| `补充 102 条缺失视频（Playwright 真实浏览器下载）` | `补齐缺失视频` | note：「102 条；用 Playwright 真实浏览器下载；来源见 …」 |
| `优化建议与应用闭环：基于特征缺口生成针对性优化建议…` | `优化建议闭环` | note |

## 三、三个需要用户确认的状态（重要）

`rework`（需返工）、`blocked`（阻塞）、`dropped`（已废弃）**必须用户确认**。

正确流程：

1. 你在对话里说明情况，并明确问一句"要标为需返工吗 / 要废弃吗"。
2. 用户同意后，再调用 `atlas_node_status` 并带 `confirm: true`。
3. 或者不带 `confirm`，工具会返回一个确认 id，同时**面板上会出现"待你确认"**，用户也可以在那里点。

**绝对不要**在用户没表态的情况下自己带上 `confirm: true`。这条规则的意义就是：树上的红黄状态必须可信，否则用户就不看了。

`reason` 要写用户能读懂的原因，不是自我辩护：
- 差：`需求变更导致需要调整`
- 好：`面板在 320px 宽度下横向溢出，用户截图反馈第 2 条`

`blocked` 还要填 `returnCondition`（什么条件下能解除）。

## 四、分支

当**原本不在计划里的事**插进来——用户临时要求、发现前置问题、外部依赖挡住——用 `atlas_branch_create`，不要用 `atlas_node_add`。

必填 `trigger`：为什么分支。这是用户回头最想不起来的东西，所以写具体：

- 差：`用户要求`
- 好：`用户试用时发现面板撑破布局，要求先修这个再继续`

分支做完用 `atlas_branch_resolve` 合回主线，节点保留——"我们分出去做了什么、合回哪里"本身就是要留下的记录。

## 五、和内置 todo_write 的关系

- **任务图谱** = 项目层面，跨会话，用户看的是它。
- **todo_write** = 当前这一轮几步的短清单，模型自己用。

两者并存，插件把 todo 只读投影到面板上。**不要**为了让 todo 和图谱一致去改 todo 的措辞，也不要因为图谱有了节点就不写 todo。

## 六、写错了怎么办

- 刚建出来、从没改过状态、没有子节点 → `atlas_node_delete` 可以删掉。
- 其他情况 → `atlas_node_status` 到 `dropped` 并写原因。**不要**试图绕过安全阀：承载过决定的节点要留痕。
- **废弃之后又需要了** → `atlas_node_status` 到 `active`，写原因，并且需要用户确认。历史里会留下"为什么又捡回来"——这比新建一个节点好，新建会把历史切断。

## 七、读

不确定现状就 `atlas_status`，别凭记忆。默认不列已完成节点；要复盘时传 `includeDone: true`。

参数用短 id（`m-3x7f` 这种）或标题片段都行，但工具返回的 id 是权威的。

## 八、对话里会出现一条 `[任务图谱]` 消息（别当成用户说的）

插件会在一步开始前，**当且仅当状态变了**的时候，往这一步里追加一条以 `[任务图谱]` 开头的短消息，大意是"当前在哪个节点、路径是什么、前置满不满足、下一步做什么"。它长这样：

```
[任务图谱] 当前：呈现：在右侧栏一眼看见全貌（m-8tj5dpb，进行中）
位置：用户面 / 呈现：在右侧栏一眼看见全貌
前置：节点状态：不止「做完 / 没做完」（已完成）
需要完整上下文时调 atlas_status；完成时用 atlas_node_done 记产出与验收。
```

怎么对待它：

- 它是**上下文**，不是新指令。别把它当作新需求去执行。
- 它**由插件生成**，用户没有输入这段话。不要回答它、不要在回复里引用它。
- 它和用户刚说的话**冲突时，以用户为准**，并顺手用 `atlas_node_update` 把图谱改对。
- 上下文被压缩之后它会再来一次，并多一行"上下文刚被压缩过"——那是在提醒你：对话被截断了，但进度没有，需要时用 `atlas_status` 把细节取回来。
