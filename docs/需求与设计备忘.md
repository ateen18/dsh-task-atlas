## 1. 问题陈述

多次对话的长任务里，对话本身被大量低价值过程信息填满（思考分析、报错、逐步细节讨论）。上下文越长，用户越容易迷失：

1. 忘记整个任务原本要做什么；
2. 不知道现在做到哪一步了；
3. 不知道当前这件事和整体任务是什么关系；
4. 如果当前任务是临时分支出来的，不记得为什么会分支。

## 2. 目标与非目标

### 目标（三块真空，社区现有插件都没做全）

- **G1 启动拆解**：项目开始时，把「核心意图 / 核心交付物 / 拆解 / 验收标准 / 不做什么」明确下来并落盘，之后任何时候都能一眼看到。
- **G2 状态语义**：节点状态不止"做完/没做完"，还包括**需返工 / 阻塞 / 已废弃**，且强制记录**原因**与**变更历史**。
- **G3 分支溯源**：临时插进来的事被显式登记为一个"分支"，记录**从哪分出来、为什么分、什么条件回归、回到哪**。
- **G4 图形化呈现**：在对话框右侧常驻、随真实进展更新的可折叠树 / 思维导图。

### 非目标（明确不做）

- 不做通用待办清单（内置 `todo_write` 已够用，我们只是**只读投影**它）。
- 不做上下文折叠 / 上下文压缩（`dsh-tree-task-flow` 已做，列 v2 评估）。
- 不做跨项目看板 / 项目记忆落盘 / 会话管理（`dsh-project-manager`、`dsh-track` 已做）。
- 不做轨迹诊断 / 死循环检测（`dsh-trajectory-governance` 已做）。

### 4.3 Q11 详解：什么叫「活动节点」

先区分两个容易混的概念：

- **节点状态**是节点自己的属性，**可以有多个节点同时「进行中」**。这是自然的：一边等测试跑完，一边改另一个文件。
- **活动节点（当前专注）是"此刻注意力在哪"**，逻辑上**只能有一个**。

右侧面板打开时要做两件事：**高亮**当前节点、**自动展开**它到根的路径（否则你得自己一层层点开去找）。问题就是"当前"从哪来。

假设树的现状是：

```
1 打通右侧栏与数据模型   ✅ 已完成
2 启动拆解              🔄 进行中      ← 进行中
  2.1 快速/详细两模式    ✅ 已完成
  2.2 访谈维度          🔄 进行中      ← 进行中
  2.3 拆解落盘          ○ 未开始
3 状态语义              🔄 进行中      ← 进行中
  3.1 状态词表          ✅ 已完成
  3.2 变更历史          ○ 未开始
```

**方案 A — AI 显式声明**

新增工具 `atlas_focus(nodeId)`，AI 开工前调一次：`atlas_focus("2.2")` 表示"我现在在做访谈维度"。

- 效果：高亮 `2.2`，自动展开 `2 → 2.2`，面板顶部显示「当前：2 启动拆解 › 2.2 访谈维度」。
- 好处：**精确、唯一、不歧义**。AI 自己知道它在干什么。
- 代价：靠 AI 自觉调。它忘了调，高亮就停在旧位置（"谎报"）。要靠 `SKILL.md` 的纪律来兜。
- 类比：**你在代码里手动打了一个书签。**

**方案 B — 按状态自动推断**

不加工具。插件自己算：所有 `status = 进行中` 的节点里，取**最近更新的那一个**高亮。

- 效果：上面这个例子里 `2`、`2.2`、`3` 都是"进行中"，只能取最近更新的（假设是 `2.2`），高亮 `2.2`。
- 好处：**零维护**，永远和数据一致，不依赖 AI 记得调工具。
- 代价：①「进行中」≠「正在看的那一个」——上面三个都是进行中，凭什么选 `2.2`？② AI 可能把 `2.2` 标成进行中就转头去别处了，"最近更新"会跟着漂，反而更不准；③ 到了「子项」这一层，AI 往往懒得逐个标进行中，选谁纯属运气。
- 类比：**用 `git status` 里哪些文件被改过，反推你现在在读哪个文件**——相关，但不是一回事。

**方案 C — A + 插件交叉校验告警**

在 A 的基础上，插件拿会话事件流做检查：

- 出现 2 个以上节点同时「进行中」→ 树上提示"当前有 3 个进行中节点，确认一下活动路径？"
- AI 声明的活动节点与最近 N 次工具调用 / 文件改动看起来无关 → 提示"你声明的当前节点是 `2.2 访谈维度`，但最近几次都在改 `src/domain.ts`（属于模块 1），要切换活动节点吗？"

- 好处：树更可信，**漂移能被发现**——这正对应 `dsh-trajectory-governance` 的"目标漂移"那套思路。
- 代价：工作量大；"无关"本质上是模糊判断，**容易误报**；误报多了你会开始无视提示，反而降低信任。

**推荐的 A + 降级到 B**

- AI 调过 `atlas_focus` → 用它的声明（精确）。
- AI 从没调过（新会话、冷启动）→ 退化成"最近更新的进行中节点"，而不是什么都不高亮。
- C 的漂移告警留到 v2 再评估。

顺带一个更根本的点：**这个"活动路径"也是将来做「把过程信息挤出上下文」的抓手。** 现在不做折叠（你选了只做三块真空），但方案 A 一旦建立，折叠边界正好就是"上一个活动节点到当前活动节点之间"——所以 A 是给 v2 留的门。

## 5. 概念模型

### 5.1 节点

```
项目 (project)                      ← 每个工作区可有多个，其中一个活动
├─ 模块 (module)                    ← 用户说的 1 / 2 / 3 / 4
│  ├─ 任务 (task)
│  │  └─ 子项 (item)                ← 最低一级，不再往下拆
│  └─ ⑂ 分支 (branch)               ← 特殊节点，见 5.3
└─ 模块 …
```

每个节点携带：

| 字段 | 说明 |
|---|---|
| `id` | 稳定短 id（如 `m-3f2a`），全树唯一 |
| `kind` | `project` / `module` / `task` / `item` / `branch` |
| `title` | 标题，**不缩略**，超长自动换行 |
| `note` | 说明（可选） |
| `status` | 见 5.2 |
| `reason` | `需返工` / `阻塞` / `已废弃` 时**必填** |
| `returnCondition` | `阻塞` 时建议填：什么条件下能解除 |
| `result` | `已完成` 时必填：产出了什么、怎么验收 |
| `origin` | 分支/子项来源：`ai` / `user` / 派生自某条消息 |
| `evidence` | 关联的会话消息 id / 工具调用 id 列表（用于"跳回对话"） |
| `history[]` | 变更历史：`{ at, by, from, to, reason }` |
| `createdAt` / `updatedAt` | 时间戳 |

### 5.2 状态机

```
        未开始 pending
           │
           ▼
        进行中 active ──────────────┐
           │                        │
     ┌─────┼─────┬──────────┐       │
     ▼     ▼     ▼          ▼       │
  已完成  需返工  阻塞     已废弃    │
   done  rework blocked  dropped   │
           │     │                  │
           └─────┴──────────────────┘
             回到 进行中
```

| `dropped` | `dropped` 留痕可查，不删除 |

- `已完成` 与 `已废弃` 都**可以继续走**：
  - `已完成 → 需返工` 是本插件的核心场景（模块 1 做完了，后来发现要优化）。
  - `已废弃 → 进行中` 是**唯一**的恢复路径，且必须写原因 + 用户确认；恢复原因进历史，
    不留成节点的「当前原因」（`active` 不该有当前原因）。见 §16.5。
- `需返工` / `阻塞` 可回到 `进行中`。
- **权限**（D3）：`进行中` / `已完成` 由 AI 自主；`需返工` / `阻塞` / `已废弃` 以及
  **从 `已废弃` 恢复**，都会生成一条"待确认"，用户确认后才生效。

### 5.3 分支

分支是"临时插进来的事"的一等公民。它不是普通子任务，因为它有三个额外语义：

1. **从哪来** (`origin`)：从哪个节点分出来的
2. **为什么来** (`trigger`)：用户临时插入 / 发现前置问题 / 外部依赖阻塞 / 别的原因 —— 必填
3. **怎么回去** (`returnCondition` + `resolvesTo`)：满足什么条件算完，完成后合回哪个节点

树上用独立徽标（⑂）+ 独立配色标出。分支完成后**不自动消失**，而是变成"已合回 <目标节点>"的状态，留痕。

### 7.2 关键接线

**host 半部**

```ts
export const name = 'task-atlas'
export const inject = ['tools', 'storageDomain', 'sessions']

export function apply(ctx: Context) {
  // 1) 持久化
  const domain = await ctx.storageDomain.open(TASK_ATLAS_SPEC)
  // 2) 工具
  ctx.tools.register(defineTool(atlasStatusTool(ctx, domain)))
  // …其余工具
  // 3) 只读投影内置 todo / goal
```

### 12.2 客户端产物的确切拆解（此前只是推断，现已验证）

DSH 把 `lib/client.js` 当**经典 `<script>`** 加载（不是 ESM）。文件唯一的职责是在页面全局
`window.__ModuleLoader__` 上**注册一个惰性 factory**：

```js
window.__ModuleLoader__.load({
  id: "dsh-task-atlas",            // 必须等于包名（启动图 row 的 id）
  factory: (require) => {
    var module = { exports: {} };
    var exports = module.exports;
    /* …CJS 包体… */
    return module.exports;
  }
});
```

要点：

- **包体必须是 CJS**：`require("react")` 这类调用解析到外壳冻结的 `PLATFORM_MODULES` 表。
- **所有模块级副作用（含 CSS 注入）必须待在 factory 闭包内**，否则会在脚本执行时就跑，而不是在物化时跑。
- 非基座模块要列进 `dsh.client.external`。
- **官方没有发布生成这个外壳的构建插件**（`dsh-client-modules` 只导出宿主侧注册表，没有任何 tsdown/rolldown 预设）。我们的做法：tsdown 输出 `format: 'cjs'`，用 `banner`/`footer` 包成上述形状（见 `tsdown.config.ts`）。

### 13.2 状态机（`src/model/status.ts`）

合法迁移表（`dropped` 是终态）：

```

rework   → active | blocked | dropped
blocked  → active | dropped
dropped  → （无）
```

三条硬规则：

1. **`done` 可以回到 `rework`**。做完了后来发现要优化，是这个插件存在的最主要理由，不能逼用户假装"从来没做过"。
2. **`rework` / `blocked` / `dropped` 强制填 `reason`**，否则返回 `REASON_REQUIRED`。一个红点不写原因，等于什么都没说。
3. **同样这三个状态需要用户确认**（分级授权），AI 单独请求时返回 `kind: 'pending'`，节点本身**一个字节不动**，等用户在面板里点确认。`done` / `active` / `pending` 由 AI 自主。

另外两点设计细节：

- **同状态重复设置是幂等的**：直接返回同一个对象引用，不追加历史、不动 `updatedAt`。工具被重复调用时不会污染审计记录。
- **`reason` 只在该状态期间挂在节点上**，回到 `active` 时清空——但**历史里永久保留**。节点显示当前状态，历史回答"为什么曾经那样"。

`done` 额外要求 `result`（产出了什么、怎么验收），缺失返回 `RESULT_REQUIRED`。

### 13.3 树（`src/model/tree.ts`）

- 层级固定 4 层，`checkAddChild` 拒绝跳级和越界（`item` 之下不能再挂任何东西）。
- 所有操作**纯函数 + 结构共享**，输入树永不被改；测试逐个断言过这一点。
- **删除安全阀**：只有 `status === 'pending' && history.length === 0 && children.length === 0` 的节点能被硬删除，其余只能标 `dropped`。理由是"当初为什么放弃"本身就是要留下的信息。
- **进度只数叶子**，且**被丢弃的节点同时离开分子和分母**。父节点是标题不是工作单元，数进去就是重复计数；把废弃的任务算进分母会让百分比在计划变动时永远爬不上去。
- **分支**是一等公民：`attachBranch` 强制要求 `trigger`（为什么分出来）且 `originId` 必须存在；`resolveBranch` 只能解一次，默认合回 `origin`。分支解决后**节点不删除**——"我们分出去修 X，修完合回这里"正是让用户不再困惑"这段横插进来的活是什么"的记录。

### 13.4 启动拆解（`src/model/charter.ts`）

七个访谈维度，`interviewFor('fast')` 走 4 个必答项，`interviewFor('detailed')` 走全部 7 个。校验分两级：

- **阻断**：`coreIntent` / `deliverables` / `decomposition` / `acceptance` 为空。
- **只警告**：某个交付物没写验收标准、某个拆解步骤是空白。理由：**因为一条交付物没写验收就不让开工，会把启动流程变成问卷**，警告放到面板上，之后再补。

### 13.5 写测试时被自己的状态机抓到的一个错

`progress` 用例的 setup 里我写了 `pending → done`，测试直接失败。这不是 bug 而是设计生效：**没开始过的事不能直接宣布完成**。改成 `pending → active → done` 后通过。这条约束值得保留。

## 16. 本轮重大变更（呈现、依赖、AI 面）与事故教训

> 本节是当前口径。§12–§15 是按时间的实现记录，数字不要当现状读。

### 16.1 呈现：从"双视图"到"三视图 + 详情卡 + 从这里继续"

- **树 / 依赖图 / 进展**三视图，共用同一份 `project`。
- **依赖图**回答"什么卡着什么"，不是"同一棵树换个画法"。第一次做成横向分栏时用户反馈
  「和树没啥差别」，第二次做成扁平 DAG 又暴露出两个真问题（见 16.2）。
- **详情卡**：面包屑、说明（缺失就明说）、可点的前置与子项、原因、解除条件、结果、分支、历史。
  之前只渲染"恰好有值的字段"，导致未开始节点点开只有标题——**结构固定比字段齐全更重要**。
- **「从这里继续」**：走会话标准属性 `inputActions`（`setDraft` + `submit`），真的把消息发进
  会话；已验证两次（用户的回复就是它发出来的）。拿不到该属性时退化为复制。

### 16.2 依赖关系（新的一等数据）

节点新增 `dependsOn: string[]`，`B.dependsOn = [A]` 读作 **A 是 B 的前置**。

- 布局交给 **dagre**（Sugiyama：分层 + 交叉最小化 + 长边虚拟节点），**两级**跑：
  外层每个模块一个大节点（模块永不错行），内层每模块单独跑（网状前置也能排序）。
- 跨模块连线走**独立通道**，互不重叠。
- **成环拒绝**（`CYCLE`）：A 等 B、B 等 A 会让两边永远开不了工。自依赖、指向不存在节点同样拒。
- **模块不承载 `dependsOn`**：模块是分组框，模块间的先后由内容推出。
  早期允许模块声明，结果与内容推出的关系**互相矛盾成一个环**——工具没报错，因为环只在
  "声明边"里检查；图是错的，数据是"对"的。教训：**两种粒度的关系不要混在一张图里**。

### 16.3 AI 面：状态注入

`agent/pre-step`（waterfall，可进入该步并追加消息）里注入一段状态，**按状态签名去重**
（签名 = 项目 + 焦点节点 + 它的状态 + 完成/进行中/返工/阻塞计数）。

- 只在签名变化时注入：改代码、写注释、连续调试都不产生噪音。
- 硬预算 **420 字**（实测约 35 token / 139 字）；有测试断言"200 节点也不膨胀"。
- **失败降级**：整个 handler 先取机器自己的 decision，任何异常都原样返回它——
  注入写错最多是"不注入"，不会弄坏任何一轮。
- **只走 user 角色**：`pre-step` 接受用户消息，`pre-call` 明确写着 cannot mutate messages。
  所以注入会出现在对话记录里，前缀 `[任务图谱]` 用来区分"这不是用户说的"；skill 第八节专门
  教模型怎么对待它（当上下文，不当指令，冲突时以用户为准）。

### 16.4 面板刷新：长轮询

- 原来 2.5 秒轮询：**不花 token**（本地 HTTP），但 99% 的响应和上次一样，真变化还晚到 2.5 秒。
- 试过 SSE：路由逻辑正确（有真实 Node 服务器测试：开流、保持、推送全过），**但宿主的 web 层
  会结束流式响应**，到了应用里每次"推送"都变成"连上就断"。
- 最终 **长轮询**：`GET /task-atlas/wait?revision=N` 挂着，写入时宿主广播修订号立刻返回。
  空闲约 6 次/分钟（原来 24 次），有变化即时到达。
- 实测：挂一个 `revision=0` 的等待 → 写入 → **431 ms** 返回 `revision=1`。

### 16.5 状态机：废弃可恢复

`dropped` 从终态改为"几乎终态"：唯一出路 `dropped → active`，必须写原因 **且**用户确认。

- 理由：彻底放弃想重做时，只能新建节点，而新建会切断历史。
- 恢复原因**进历史**，不留成节点的「当前原因」（`active` 不该有当前原因）。
- 顺带修了一个概念混淆：`keepsReason` 之前同时管"历史要不要记原因"和"节点要不要留原因"，
  恢复场景下这两个答案相反，已拆成两个判断。

### 16.6 数据兼容：改名差点毁掉数据

把字段 `charter` 改名成 `breakdown` 时**没有迁移磁盘上的数据**。schema 里新键必填，
于是每条记录校验失败 → 域打不开 → 插件启动失败 → 面板空白。

- 用户看到的是"数据没了"，实际一个字节都没坏。
- 修法：**读取端认旧键**（`breakdown ?? charter ?? null`），不改用户数据。
- 同时把域的 `invalidRecords` 改为 `backup-and-skip`：一条坏记录不该让整个插件消失。
- 新增 `scripts/check-storage.mjs`：一条命令校验真实记录，把"树空了"从猜谜变成测量。

### 16.7 启动韧性：一个服务缺席 = 整个插件静默消失

`inject = ['tools','storageDomain','webServer']` 的写法，在 DSH 夜间升级后变成了致命缺陷：
只要有一个服务没到位，`apply()` 永不执行——**不报错、不打日志、没有工具、没有路由**。

- 现在只有 `tools` 是硬依赖，其余通过 `ctx.inject` 晚绑定；工具绑定到 `DelegatingStore`，
  存储晚到时换入真身，缺了就返回可读错误。
- 启动失败写 `~/.dsh/task-atlas-startup.log`，并且 `/task-atlas/state` 直接返回
  `STARTUP_FAILED: <原因>`——**面板是唯一用户会看的地方，失败必须能出现在那里**。
- `apply()` 整体 try/catch：一个坏记录、一次 API 改名，都不该拖垮整行。

### 16.8 打包边界：内联失败 = 应用起不来

客户端 bundle 留了一个 `require("@dagrejs/dagre")`：tsdown 默认把 `dependencies` 当外置。
而客户端的 `require` 只解析平台冻结表 → 加载即抛 → **整个应用无法启动**，用户只能禁用插件才能进来。

- 修：`deps.alwaysBundle: ['@dagrejs/dagre']`。
- 更重要的修：`scripts/check-client-bundle.mjs` 挂在 `pnpm run build` 末尾，
  **出现白名单外的 require 就让构建失败**。这类错误的代价远高于一次构建失败。

### 16.9 偏离检测：两个通道，不同的代价

| | 给用户（面板） | 给模型（注入） |
|---|---|---|
| 信号 | 用户消息与项目词汇零重叠，连续 2 条，长度 ≥ 8 字；另有"自上次 atlas 调用以来的步数 ≥ 20" | 由用户侧触发，或步数触发 |
| 阈值 | 低——猜错成本只是被驳回一次 | 高——猜错会让模型学会无视提示 |
| 措辞 | **问句**：要登记成新项目，还是继续主线？ | **陈述**：先问再答，拿到答复再继续 |

- 词汇表 = 项目自己的词（节点标题 + 拆解文本）切 2–4 字片段，滤掉"任务/项目/继续"这类
  谁都会用的词，**并且丢弃以虚词开头的片段**。后者是实打实踩出来的：片段「的问」命中了
  "无关的问题"，把离题消息判成相关，一次假阴性就让连续计数清零，整个功能失效。
- **判定必须在 `agent/pre-step` 里对"这一步要回答的消息"做**，不能在 `session/event` 里做：
  事件是异步的，观察可能晚于这一步的决策，于是模型先答完、下一轮才被问——
  这正是"先斩后奏"。用户明确指出后已改。

> **设计诚实**：这些信号的误报率没有经过真实使用检验。已知脆弱点：同义词（说"侧边栏"
> 而不是"面板"）会被判离题。

### 16.10 事故教训（五个，同一个形状）

这一轮出过五次事故，形状完全一样：**我报告的成功，和我实际做到的事不是一回事。**

| 事故 | 用户看到 | 真实原因 |
|---|---|---|
| 改字段名 | 数据全没 | 读取端只认新键，记录校验失败 |
| 服务声明过强 | 面板空白 | inject 未满足，插件静默不激活 |
| dagre 外置 | 应用无法启动 | 客户端 require 平台外模块 |
| 重启脚本 | 报错弹窗，重启无效 | 强杀宿主 + 脚本是宿主子进程，跟着死 |
| SSE | 面板不刷新 | 宿主掐断流式响应，客户端静默退化 |

**共同的修复方式不是"下次小心"，而是把判断变成测量：**

- `pnpm run build` 里的客户端护栏（外部 require 即失败）
- `scripts/check-storage.mjs`（记录是否符合 schema）
- `scripts/check-running-build.mjs`（运行的进程是不是当前构建 + 路由是否真的应答）
- 启动失败必须出现在面板上，不能只写日志
- 不进 `atlas_node_done`，除非有可复述的证据（用户点击、注入原文、探测结果）

`scripts/restart-desktop.ps1` 现在**不杀进程**，文件头写清了三个原因：关窗口只是收进托盘；
强杀宿主会让桌面端弹"host exited"；脚本本身是宿主的子进程，会跟着一起死。
**重启是用户的操作，验证是我的测量。**

### 16.12 依赖图删掉了（做过又删的地方，值得记）

**结论**：依赖关系值得保留，依赖**图**不值得。

过程是这样的：

1. 第一版横向分栏，用户反馈"和树没差别"。
2. 第二版换成真正的 DAG：模块当分组框、两级 dagre 布局、跨模块走独立通道、点节点高亮上下游。
3. 用户在真实工作区用了几次，反馈"整体还是不好阅读"——于是删掉。

**为什么删**：图适合回答"全局结构长什么样"，但用户的真实问题是"这块现在能不能开工、在等谁"。在一个几百像素宽、又高又窄的侧栏里，后者用**列表**比用**图**回答得快一个量级。图在这个尺寸下只会变成一堆线和一堆小字。

**替代方案（现在生效）**：点开任一节点，详情卡里有「本节点前置依赖（N）」，每条是

```
● 节点状态：不止做完/没做完        已完成   · 需要：状态词表与合法转移规则
```

- 圆点与文字都用该前置**自己的状态色**（绿=已完成 / 蓝=进行中 / 红=阻塞 / 琥珀=需返工 / 灰=未开始）
- 可点，直接跳到那个前置
- 带上「需要什么」——这让"前置"不是排期的猜测，而是可核对的依赖

**顺带删掉的**：`graph-view.tsx`、`graph-layout.ts`、`@dagrejs/dagre` 依赖、`neighboursOf` / `assignLayers` / `layerColumns` 三个只服务于图的函数及其测试。

**代价与收益**：客户端产物从 **158 kB → 70 kB**（gzip 44.4 → 19.0）；少了一条第三方库的版本兼容链；`assignLayers` 那份最长路径实现也一起没了，而它本来就是为画图而写的。

**一句留给以后的话**：一个"看起来更全面"的视图，如果回答不了用户当下的问题，它的成本（认知 + 体积 + 维护）就是纯付出。删掉比留着更难，但更对。
